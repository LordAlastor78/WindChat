**Problema H2.1 — CRÍTICO: senderId se propaga con valor NULL cuando connectionId es None**
- En `handleMessage` (línea 413-419): `senderId = meta.connection_id.lock().await.clone()`
- El `connection_id` del handshake es `Option<String>` (línea 291-294): si el cliente NO envía `connectionId`, queda `None`
- El JSON resultante tendrá `"senderId": null`
- El cliente (`websocket.ts:343`) filtra ecos con `msg.senderId === this.connectionId` — si `senderId` es `null` y `this.connectionId` es un UUID, NUNCA coincide → **el cliente recibe su propio eco y lo intenta descifrar con la cadena de recepción, avanzando el ratchet de recepción → desincronización**
- El `handleEncryptedMessage` (websocket.ts:343-345) devuelve silenciosamente si coincide senderId, pero si es `null` no coincide y procede a `crypto.decrypt(msg.iv, msg.ciphertext, msg.counter)` con un counter que el cliente nunca envió.
- **Causa raíz:** el relay confía en que `connectionId` siempre está presente (el protocolo lo marca `?` opcional), pero no hay defensa para el caso `None`.
- **Cómo se reproduce:** un cliente legacy o un test que omita `connectionId` en el handshake → recibe su propio eco → desincroniza el ratchet.
- Evidencia: relay-rust/src/main.rs:413 (`connection_id: Mutex<Option<String>>`) + línea 419 (`"senderId": sender_id` donde sender_id puede ser None/null)
- Confirmado: MUY PROBABLE (el código Rust serializa Option<String> como null en JSON)
- Confianza: ALTA

**Problema H2.2 — ALTO: No hay validación de Origin en el WebSocket handshake**
- El relay Rust usa `accept_async(stream)` (línea 137) que acepta CUALQUIER conexión TCP sin inspeccionar el Origin HTTP.
- Un relay público (no localhost) permitiría a cualquier origen conectarse y unirse a rooms.
- El server Node también carece de esta validación (ver Fase 3).
- Confianza: ALTA (ausencia de código)

**Problema H2.3 — ALTO: No hay heartbeat WS nivel protocolo (solo ping/pong binario)**
- El relay responde a `Message::Ping` con `Message::Pong` (línea 188-191) y a `Message::Pong` (línea 192-195).
- El heartbeat de aplicación (`ping`/`pong` JSON) existe pero el relay NO envía pings periódicos si el cliente no los inicia.
- El server Node SÍ envía pings periódicos (línea 204-228), pero el relay Rust NO → **inconsistencia entre capas**. El relay Rust puede mantener sockets muertos abiertos indefinidamente si el cliente no envía pings.
- La única defensa es `HEARTBEAT_TIMEOUT` (60s) basado en `last_seen` activado por `pong` o datos entrantes, pero si un cliente se cuelga sin enviar nada, tarda 60s en ser limpiado.
- Confianza: ALTA

**Problema H2.4 — MEDIA: Race condition en cleanup de rooms**
- `handle_disconnect` (línea 457-481) itera `rooms.iter_mut()` y hace `break` después del primer `remove()`.
- Si un cliente está en múltiples rooms (no posible con MAX_USERS_PER_ROOM=2, pero el código no impide `connection_id` duplicado en distintas rooms), solo se limpia la primera.
- Más importante: el `seen_connection_ids` HashSet **nunca se limpia** cuando una room se elimina (línea 469: `rooms.remove(&rid)` borra la room entera, incluyendo su HashSet, así que está OK). Pero si un cliente se reconecta con el mismo `connectionId` a una room que ya fue eliminada (porque quedó vacía), el `seen_connection_ids` se recrea vacío → **se trataría como NUEVA conexión, no como reconexión** → re-handshake → desincronización de ratchet.
- Evidencia: handle_disconnect línea 468 (`if room.clients.is_empty() { rooms.remove(&rid); }`) elimina la room y su HashSet.
- Confianza: MEDIA (requiere timing específico: room se vacía, se elimina, luego reconexión con mismo connectionId)

**Problema H2.5 — BAJA: El relay Rust no reenvía el tipo `disconnect` del cliente**
- El protocolo (`shared/protocol.ts:111-114`) define `DisconnectMessage` con `type: "disconnect"`.
- El relay Rust maneja `"disconnect"` (línea 266: `Ok(handle_disconnect(...))`) → cierra la conexión al relay, pero NO le envía al peer un mensaje de `disconnect` antes de cerrar.
- Espera: al cerrar el WS, el peer recibe `peer_disconnected` del `handle_disconnect`. Esto está bien.
- Pero el `DisconnectMessage` del cliente nunca se difunde como tal (solo como cierre de socket). Esto es semánticamente correcto pero el server Node hace lo mismo (handleDisconnect no envía "disconnect").
- Confianza: BAJA (diseñado así, no es un bug)

#### 4.1 Inicialización / conexión WS

**Problema H4.1 — MEDIO: `serverUrl` construido con `window.location` es incorrecto en Tauri**
- `connectToChat` (main.ts:332, 400): `const serverUrl = "${wsProtocol}//${window.location.host}"`.
- En Tauri, `window.location.protocol` es `tauri:` → `window.location.host` es `""` (o el origin tauri). El WS resultaría `ws:///` o `wss://app.localhost` → **falla la conexión**.
- En Tauri debería usar `ws://127.0.0.1:8080` (el relay sidecar). No hay detección de entorno Tauri para la URL del WS.
- El `isTauri()` helper existe (línea 1997) pero **no se usa para determinar serverUrl** — se usa solo para share link.
- Confianza: ALTA (ausencia de lógula Tauri para serverUrl)

**Problema H4.2 — ALTO: `handleReconnection` destruye el ratchet si `!crypto.isReady()` por un error transitorio**
- websocket.ts:619-628: `if (!this.crypto.isReady()) { this.crypto.destroy(); this.crypto = new CryptoManager(); }`.
- Si `crypto.isReady()` retorna `false` por un estado inconsistente (ej. `sendChain` undefined por un error de deriva), el ratchet se REINICIA → counter 0 → **desincronización permanente con el peer**.
- El comentario dice "solo recreamos el CryptoManager si NUNCA se derivó" pero `isReady` verifica `sendChain !== undefined && recvChain !== undefined`. Si una de las dos se perdió (pero no ambas), `isReady() = false` → se destruye el ratchet VIGENTE.
- Confianza: ALTA (el código de defensa es frágil)

**Problema H4.3 — MEDIO: No hay cleanup de `localMessages` Map en `beforeunload`**
- main.ts:40: `const localMessages = new Map<string, any[]>()`.
- Los mensajes se almacenan en memoria (copia local de metadatos) + en `Store` (localStorage).
- En `beforeunload` (línea 1613) solo se llama a `sessionManager.all()` y `disconnect()`. **Nunca se limpia `localMessages`**.
- Esto es mínimo (es memoria efímera del proceso), pero `localMessages` se sincroniza con `Store` y en reconexiones puede tener datos stale. No es crítico.
- Confianza: MEDIA

**Problema H4.4 — BAJA: `connectionId` es UUID.randomUUID() → no persiste entre recargas de página**
- websocket.ts:49: `private connectionId = crypto.randomUUID()`.
- Si la pestaña se recarga (F5) y la room todavía existe en el server (el peer se quedó), el cliente presenta un `connectionId` NUEVO → el server trata la conexión como NUEVA → re-handshake ECDH → desincroniza el ratchet.
