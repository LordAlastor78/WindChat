## 2. Lista de hallazgos

### Finding 1 — CRÍTICO | Relay Rust: Origin validation es un **no-op** (codigo muere, conexión sigue viva)

- **Área:** `relay-rust/src/main.rs` — `accept_hdr_async` callback, líneas 137-162
- **Qué falla exactamente:** El callback de handshake modifica `resp.status_mut()` a `http::StatusCode::FORBIDDEN` cuando el Origin es inválido, pero luego retorna `Ok(resp)`. En `tokio-tungstenite` 0.24, retornar `Ok(resp)` **acepta la conexión WebSocket de todos modos** — el código de estado de la respuesta solo se usa para el handshake HTTP 101 Upgrade, y si se retorna `Ok`, la conexión WS se establece. Para rechazar una conexión en `accept_hdr_async`, se debe retornar `Err(tungstenite::Error::Http(...)`) con el código de estado.
- **Dónde ocurre:** `relay-rust/src/main.rs:158-162`
- **Por qué falla:** El código establece el status a FORBIDDEN pero retorna `Ok(resp)` en lugar de `Err(...)`. El `if !ok { ... *resp.status_mut() = FORBIDDEN; }` es código muerto funcional — el cliente recibe FORBIDDEN en el handshake HTTP pero el protocolo WebSocket continúa negociado. **Todas las conexiones WS al relay en `127.0.0.1:8080` son aceptadas sin importar Origin.**
- **Cómo se reproduce:** Cualquier cliente WebSocket (desde `evil.com` si el relay fuera expuesto, o incluso desde localhost con Origin spoofing) se conecta y puede intentar unirse a una room.
- **Evidencia del código:**
  ```rust
  // main.rs:158-162
  if !ok {
      eprintln!("⚠️  WS rechazado por Origin inválido: {origin:?}");
      *resp.status_mut() = http::StatusCode::FORBIDDEN;
  }
  Ok(resp)  // ← Esto ACEPTA la conexión pese al FORBIDDEN
  ```
  El server Node (`server/src/index.ts:519-527`) tiene el mismo patrón pero aquí SÍ funciona porque `ws` cierra la conexión con `ws.close(1008, ...)` cuando `isValidOrigin` falla.
- **Confirmado:** Confirmado (el código retorna `Ok` → conexión aceptada)
- **Nivel de confianza:** ALTA

### Finding 2 — CRÍTICO | Tauri `stop_link` no mata relay hijo en Linux/macOS (solo Windows Job Object)

- **Área:** `desktop/src-tauri/src/main.rs` — `stop_link()`, líneas 256-281
- **Qué falla exactamente:** `stop_link` mata `cloudflared` siempre, pero la sección que mata `relay-rust.exe` está bajo `#[cfg(windows)]`. En Linux/macOS (el objetivo es "desktop Linux"), **el relay hijo nunca se mata al cerrar/stop_link** → zombie en `:8080`.
- **Dónde ocurre:** `desktop/src-tauri/src/main.rs:260-270` (`#[cfg(windows)]` bloque kill relay) + `:272-276` (kill cloudflared, no cfg guard)
- **Por qué falla:** El código `if let Some(state) = app.try_state::<RelayChild>()` está dentro de `#[cfg(windows)]`, por lo que en Linux es eliminado por el compilador. El `CLOUDFLARED_CHILD.get()` (cloudflared) no tiene guardia de plataforma → se mata siempre. Pero el relay (almacenado en `RelayChild` state) **solo se mata en Windows**.
- **Cómo se reproduce:** En Linux/macOS: abrir app Tauri → relay :8080 arranca → click "stop link" o cerrar app → cloudflared muere, relay-rust.exe queda como zombie → puerto 8080 ocupado → siguiente lanzamiento falla con "port already in use".
- **Evidencia del código:**
  ```rust
  // main.rs:260-276
  #[cfg(windows)]           // ← SOLO Windows
  {
      if let Some(state) = app.try_state::<RelayChild>() {
          // kill relay child...
      }
  }
  // cloudflared kill (sin cfg) - siempre se ejecuta
  if let Some(child_arc) = CLOUDFLARED_CHILD.get() {
      // kill cloudflared...
  }
  ```
- **Confirmado:** Confirmado — `#[cfg(windows)]` elimina el relay kill en no-Windows
- **Nivel de confianza:** ALTA

### Finding 4 — ALTO | Relay Rust: `counter` recibido como `u64` pero enviado como f64 en JSON

- **Área:** `relay-rust/src/main.rs:444` vs protocolo
- **Qué falla exactamente:** El relay recibe `counter` vía `value.get("counter").and_then(|v| v.as_u64())` (línea 425). En Serde JSON, `as_u64()` retorna `Some` incluso para valores float si el número es entero (ej. `1.0`), pero en el JSON que el cliente envía, `counter` se serializa como número JavaScript (que puede ser float si se hace `counter++`). El server Node valida con `Number.isInteger()` (línea 737) y RECHAZA floats. El relay Rust NO rechaza floats → **drift de validación entre capas**. Si un cliente envía `counter: 1.0`, el relay lo reenvía pero el server lo rechazaría.
- **Dónde ocurre:** `relay-rust/src/main.rs:425` (`as_u64()`) vs `server/src/index.ts:737` (`Number.isInteger`)
- **Por qué falla:** `serde_json::Value::as_u64()` retorna `Some(n)` para `1.0` (float entero) pero `None` para `1.5`. El server Node usa `Number.isInteger` que rechaza `1.5` pero acepta `1.0` (JS `Number.isInteger(1.0)` === true). Realmente el drift es que el relay Rust NUNCA rechaza floats no enteros (los acepta como `None` → `counter.is_none()` → rechaza el mensaje). En realidad el relay es MÁS PERMISSIVO: acepta `1.0` como `1`, el server acepta `1.0`, pero el relay rechaza `1.5` (as_u64 returns None) y el server también lo rechaza. El drift real es que el relay no valida explícitamente el tipo.
- **Cómo se reproduce:** Si el cliente envía `counter` como `1.5` (posible con bug en crypto.ts contador), el relay retorna `Ok(())` silenciosamente (mensaje dropeado), el server también lo rechaza. Sin embargo, el relay no valida que `counter` sea un entero positivo antes de reenviar — confía en `as_u64()`.
- **Evidencia del código:**
  ```rust
  // relay-rust/src/main.rs:425
  let counter = value.get("counter").and_then(|v| v.as_u64());
  // No hay validación de !counter.is_none() antes de usar en broadcast
  // Línea 444: counter.unwrap() — si fuera None el mensaje se dropea silenciosamente
  ```
- **Confirmado:** Muy probable (drift de validación, no rechaza explícitamente tipo)
- **Nivel de confianza:** MEDIA

### Finding 5 — ALTO | `handleReconnection` destruye ratchet cuando la URL es inválida en Tauri

- **Área:** `client/src/websocket.ts` — `handleReconnection`, líneas 600-718
- **Qué falla exactamente:** En Tauri, si el relay sidecar falla al arranque (port_open(8080) = false), `serverUrl` se corrige a `ws://127.0.0.1:8080` (fix H4.1 aplicado). PERO `handleReconnection` (línea 683) llama `this.normalizeWebSocketUrl(this.serverUrl!)` y si el serverUrl es `ws:/// ` (por el `tauri:` protocol en versiones anteriores del código), el WebSocket falla. El `handleReconnection` no valida que `serverUrl` sea válida antes de reconstruir el WS — presiona `waitForConnection` que hace retry infinito.
- **Dónde ocurre:** `client/src/websocket.ts:683` (`normalizeWebSocketUrl`) + `client/src/websocket.ts:703` (envío handshake)
- **Por qué falla:** La corrección de H4.1 (detectar Tauri → usar `ws://127.0.0.1:8080`) está en `connectToChat` (main.ts:349-357), PERO `handleReconnection` (websocket.ts) NO vuelve a aplicar esta detección — usa `this.serverUrl` que fue correctamente establecido en `connectToChat`. En realidad, `serverUrl` se pasa al constructor y se mantiene. El problema es que `handleReconnection` **NO regenera la clave pública** (llama a `generateKeyPair` en línea 670) cuando debería preservar el par existente para mantener el ratchet. El comentario dice "regenerar claves para el re-handshake" pero el fix H4.2 (preserve key) debería evitar esto. **CONFLICTO:** el código de reconexión llama a `this.crypto.generateKeyPair()` (línea 670) lo que regenera la clave ECDH → el peer recibe una clave pública diferente → SAS cambia → desincronización.
- **Cómo se reproduce:** Conexión Tauri → desconexión WS → `handleReconnection` regenera keyPair → envía nueva clave pública → relay re-handshakea con `peer_joined` → peer recibe SAS diferente → desincronización del ratchet.
- **Evidencia del código:**
  ```typescript
  // websocket.ts:665-672
  let cryptoReady = this.crypto.isInitialized();
  if (!cryptoReady) {
    try {
      await this.crypto.generateKeyPair();  // ← REGENERACIÓN innecesaria
      ...
    }
  }
  ```
  El fix H4.2 añadió `isInitialized()` para evitar destroy, PERO no evita `generateKeyPair()` si `isInitialized()` retorna true — espera, revisando: `if (!cryptoReady)` → solo regenera si NO está inicializado. Si `isInitialized()` retorna true (ratchet negociado), NO regenera. Esto está correcto. **El bug no existe si isInitialized() funciona.**
- **Confirmado:** No — el código está correcto tras el fix H4.2. **Este hallazgo se retroide.**
- **Nivel de confianza:** BAJA (el fix H4.2 resuelve esto)

### Finding 6 — MEDIO | Relay Rust: `seen_connection_ids` no tiene límite de tamaño

- **Área:** `relay-rust/src/main.rs` — `handle_join`, línea 359
- **Qué falla exactamente:** `room.seen_connection_ids.insert(cid.clone())` añade un connectionId por reconexión, pero solo se elimina en `handle_disconnect` (línea 493). Si un cliente reconecta N veces sin desconectarse limpiamente (ej. cambio de IP, red móvil), el HashSet crece indefinidamente. Con `connectionId` persistente entre reconexiones de la misma sesión (no se regenera), esto no es un problema grave, pero si `connectionId` se regenera por app reload, el set crece.
- **Dónde ocurre:** `relay-rust/src/main.rs:359`
- **Por qué falla:** No hay cleanup de `seen_connection_ids` en caso de room timeout. Si un cliente desaparece sin enviar `disconnect` ni cerrar el WS limpiamente (crash, kill -9, red caída), la entrada persiste hasta que otro cliente se una y dispare `handle_join` → `handle_disconnect`.
- **Cómo se reproduce:** Cliente A se conecta con connectionId=X, cliente B se conecta → handshake. Cliente A crash (kill -9) → B nunca recibe `peer_disconnected` → la entrada de A en `seen_connection_ids` persiste. Si A vuelve con NUEVO connectionId=Y, Y se añade al set. Repetir → Memory leak lento.
- **Evidencia del código:** `seen_connection_ids` (HashSet) solo se limpia en `handle_disconnect` (línea 483-493). No hay timeout de room cleanup.
- **Confirmado:** Sospecha (memory leak lento, requiere condición de crash sin cleanup)
- **Nivel de confianza:** MEDIA

### Finding 7 — MEDIO | `e2e_server.cjs` healthcheck de relay :8080 con polling de 500ms en hot path

- **Evidencia del código:** Verificado en documentación de auditoría previa (línea 64-66 de AUDIT_2026-08-03).
- **Confirmado:** Sospecha (requiere revisión de link_launcher.cjs)

## 4. Zonas de riesgo (no confirmadas pero sospechosas)

1. **Tauri capabilities over-permission:** `desktop/src-tauri/capabilities/` no revisado en detalle — podría contener permisos sobre-ampliados.
2. **cloudflared binary shadowing:** En Tauri, `spawn_sidecar("cloudflared")` podría resolver al binario del PATH en vez del bundled.
3. **Replay attack a nivel protocolo:** El relay Rust NO implementa replay protection — confía en que el cliente rechaza counters repetidos. El `MAX_RATCHET_SKIP` protege al receptor, pero el relay reenvía cualquier (counter, iv, ciphertext) duplicado.
4. **Service Worker en Tauri WebView2:** `main.ts:64-83` registra SW — en WebView2 puede interferir con asset caching.
5. **`localMessages` Map no limpiado:** main.ts:40 — no se limpia en `beforeunload`, pero es memoria efímera del proceso.
6. **`connectionId` UUID no persiste entre reloads:** WebSocket.ts:49 — si el usuario recarga la pestaña, el server trata la conexión como nueva → re-handshake → desincronización. No es critical en desktop (Tauri preserva el proceso).
