## 1. Veredicto

**Rehacer desde cero — FugazChat P2P.** El rewrite no es el camino fácil; es el camino **más barato a largo plazo** por la magnitud de la deuda de cohesión. WindChat ha acumulado tres fracturas estructurales que un parche no puede sellar:

1. **Un monolito UI de 2212 líneas (`main.ts`)** que conoce de todo: DOM, WebSocket, WebCrypto, Tauri invoke, localStorage, Service Worker, clipboard, notificaciones, markdown, i18n, theming.
2. **Una UI legacy duplicada (`chat.html`, 2170 líneas)** con CSS inline + JS inline que **no importa ningún módulo moderno** → `main.ts:237` redirige usuarios a una UI sin E2E fixes aplicados.
3. **Una documentación que valida bugs como fixes** (`AUDITORIA_REPORTE.md` afirma "10/10, 96/96" pero real es 94/94 y 2 bugs críticos no están aplicados).

Estas fracturas no son bugs aislados — son **síntomas de un proceso de vibecoding que priorizó features sobre arquitectura**, y cada intento de refactorizar incrementalmente (como el AUDITORIA_REPORTE.md §5.8 "refactor main.ts" → postergado por "alto riesgo de regresión") confirma que la deuda supera el coste de reiniciar.

## 5. Viabilidad técnica de libsignal en browser (verificado)

### 5.1 Opciones disponibles

| Paquete | Estado | Browser | Node | Android | Licencia | Notas |
|---|---|---|---|---|---|---|
| `@signalapp/libsignal-client` | ⚠️ **Oficial Signal** | ❌ "unsupported" fuera de Signal apps | ✅ | ✅ (libsignal-android) | AGPL-3.0 | Signal Desktop lo usa. Pero "Use outside of Signal is unsupported." |
| `@privacyresearch/libsignal-protocol-typescript` | ✅ Activo (0.0.16, 2021-2024) | ✅ (WebCrypto) | ✅ | ❌ (no Java) | GPL-3.0 | Fork de Signal. Funciona en browser. StackOverflow confirma uso en React. |
| `libsignal-protocol-javascript` | ❌ **Archivado (2021)** | ✅ | ✅ | ✅ | GPL-3.0 | "Replaced by libsignal-client." |

### 5.2 Veredicto para FugazChat 2.0

**`@privacyresearch/libsignal-protocol-typescript` es la opción correcta para browser/desktop.** Es GPL-3.0 (compatible con el AGPL-3.0 del proyecto), funciona en browser via WebCrypto, usa WebCrypto para AES/HMAC/RNG (no asm.js bloat), y está validado en producción (usado en forks de Signal como Molly/Senya).

**No usar `@signalapp/libsignal-client`** en browser — el README dice explícitamente "Use outside of Signal is unsupported". Técnicamente funciona (Signal Desktop lo usa), pero no hay garantía de compatibilidad browser y el native Rust binding (Neon) necesita rebuilds cross-platform.

### 5.3 Implementación P2P Signal (adaptada de positive-intentions.com)

El artículo de **positive-intentions.com** (fuente autoridad, citado en el MIGRATION.md de WindChat) documenta exactamente el patrón necesario:

**X3DH adaptado a P2P (3 DH, sin prekeys, sincronizado sobre DataChannel):**
1. Ambos peers generan identity keys (X25519 + Ed25519) + signed prekey
2. Intercambian bundles sobre WebRTC DataChannel (`webrtcDataChannel.send(JSON)`)
3. Verifican signatures Ed25519 (anti-MITM)
4. 3 DH: `identity×signedPrekey`, `ephemeral×identity`, `ephemeral×signedPrekey`
5. HKDF de los 3 outputs → shared secret → Double Ratchet initialization

Este patrón es **compatible con libsignal**: el `SessionBuilder` acepta prekeys manuales, y para P2P el exchange es real-time sobre DataChannel (no necesita servidor de prekeys). El positive-intentions confirma: "The solution is to perform X3DH as a synchronous, real-time handshake over an already-established WebRTC data channel."

## 6. Viabilidad de serverless P2P con cloudflared

### 6.1 Mecanismo técnico

El `tools/link_launcher.cjs` ya implementa el patrón de **cloudflared Quick Tunnel**. El mecanismo:

```javascript
// link_launcher.cjs reproduce el patrón
const proc = spawn('cloudflared', ['tunnel', '--url', 'http://localhost:4183']);
// cloudflared captura la URL *.trycloudflare.com del stderr
// expone POST /share → devuelve la URL pública
// expone POST /stop → mata cloudflared
```

**Cloudflare Quick Tunnel** da:
- Una URL efímera `https://[hash].trycloudflare.com` en ~3-5 segundos
- HTTP/WebSocket forwarding de `localhost:PORT` a la URL pública
- **Se cierra al matar el proceso cloudflared**

### 6.2 Viabilidad serverless P2P

| Requisito | WindChat actual | FugazChat 2.0 |
|---|---|---|
| **Signaling efímero** | Necesario (SDP/ICE exchange) | ✅ cloudflared Quick Tunnel expone un WebSocket efímero para signaling |
| **Túnel P2P** | No (todos van al relay WS) | ✅ Tras el handshake, peers se conectan vía STUN/ICE directo |
| **Cleanup** | Manual (POST /stop → taskkill) | ✅ Tauri invoke o `WindowEvent::Destroy` mata cloudflared + signaling hijo |
| **NAT traversal** | N/A (relay central) | STUN público (Google `stun:stun.l.google.com:19302`) + trickle ICE + TURN fallback |

**El patrón ya existe parcialmente:** el `link_launcher.cjs` hace exactamente lo necesario — spawnea cloudflared, captura la URL, la retorna via `/share`. Solo hay que:
1. Reemplazar `http://localhost:4183` (server Express proxy) → `http://localhost:4301` (signaling efímero Rust WebSocket)
2. Hacer que el signaling server se cierre 60s tras el handshake (TTL)
3. Mover la lógica de `link_launcher.cjs` a `desktop/src-tauri/src/main.rs` (Tauri invoke) + `cloudflared` sidecar

### 6.3 Riesgos de NAT traversal

| NAT type | STUN works? | Fallback |
|---|---|---|
| Cone NAT | ✅ | — |
| Restricted NAT | ✅ (con conocimiento del peer) | — |
| Port-restricted NAT | ✅ (con trickle ICE) | — |
| **Symmetric NAT** | ❌ | **TURN efímero** (coturn como subprocess, ~5MB) |

El riesgo real es symmetric NAT (~9% de usuarios, según estudios de Mozilla). El fallback es un TURN efímero (coturn) que se levanta con la app y se cierra al terminar — añade ~5MB + una dependencia Rust. El `e2e_f2_cors.js` ya testea que el CORS del launcher funcione → patrón válido para validar.

## 9. Lecciones del vibecoding (aprender de los errores)

| Error del vibecoding | Lección para FugazChat 2.0 |
|---|---|
| **"Compila ≠ funciona"** (Origin validation no-op: `Ok(resp)` con FORBIDDEN compila pero no rechaza) | **CI obliga tests de comportamiento**: Origin inválido → conexión rechazada (no solo `cargo check`). |
| **Docs sobreestiman** (AUDITORIA_REPORTE "10/10" con fixes inventados) | **Nada de "✅ CORREGIDO" sin test + commit hash + comando de verificación.** Si no hay test que valide, no se escribe. |
| **Tests mocks ≠ reales** (websocket.test.ts mockea crypto) | **Tests de cripto con libsignal sobre DataChannel real.** Mocks solo para lógica no cripto. |
| **UI paralela** (chat.html vs main.ts) | **Un solo entry point.** Vite build → 1 SPA. Nada de HTML estático con JS inline. |
| **Dualidad web/desktop** (5 scripts) | **Tauri WebView ejecuta el mismo TS.** Zero divergence. El `.exe` y browser comparten código fuente. |
| **Scripts operacionales gigantes** (run.ps1 = 1089 líneas) | **Diagnostic separado de runtime.** `scripts/diagnose.cjs` opcional, no en el path de build. |
| **`#[cfg(windows)]` silencioso** (stop_link no funciona en Linux) | **CI cross-platform:** `cargo check` en Linux + Windows + macOS. Si no se prueba, no se mergea. |
| **connectionId volátil** (no persiste entre reloads) | **State manager unificado** (`appState` con observables). Nada de globals dispersos entre modules. |

## 10. Conclusión

**El núcleo de WindChat es sólido** (criptografía 10/10, tests reales para crypto, protocolo sincronizado). **La integración es frágil** (monolito UI, chat.html legacy, dualidad web/desktop, docs contradictoria).

**Rehacer FugazChat 2.0 no descarta lo bueno** — el 70% del valor (crypto, fileManager, markdown, sync, tests baseline, scripts E2E) se salva. Pero el 30% que hay que deshacer (monolito, legacy, dualidad) es **más caro arreglarlo que reescribirlo** con las lecciones aprendidas.

La decisión no es entre "arreglar" o "tirar todo" — es entre **parchear una fractura estructural** (riesgo: seguir acumulando deuda) o **rediseñar con disciplina** (tests antes que docs, UI modular, un solo entry point, CI cross-platform).

> **Recomendación:** Confirmar la arquitectura FugazChat 2.0 (Signal Protocol + WebRTC P2P + SQLCipher + modos efímero/persistente + Tauri desktop) → proceder con **Fase 0** (validación mínima: libsignal + WebRTC localhost). Si Fase 0 pasa, el rewrite está validado. Si falla, reevaluar (puede que `@privacyresearch/libsignal` no funcione en WebView de Tauri).
